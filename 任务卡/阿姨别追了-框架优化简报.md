## 1. 一句话结论

链路是通的（自测 15/15 真通过），代码**也说不上「烂」**——它是**换代进行中**：地基已经按新方案在搭（物件清单化、按编号找件），只是老写法留下的收尾活还没干完。

看起来「到处都坏」，其实**只有四处真的在坏**：

1. **三处真源打架**：`run/main_scene`、文档、清单各指一张图，不知道该信谁（P0-1）。
2. **总管只登记不注销**：重开几次后账本里全是已删节点，会报 freed instance（P0-2）。
3. **箱子层号写死 `1`**：放到第 2 层薄板上直接穿透（P1-3）。
4. **`crawl` 和 `down` 都绑 S**：梯子口按 S 会同时触发两个动作（P2-2）。

**这四处修完，游戏行为就是对的。**

剩下的（`class_name` 类型契约、状态机替布尔堆、抽共用移动件、注释瘦身、自测搬真图）不属于「正在坏」，属于**「从能跑变得更好维护」**：不做也不会崩，只是每加一个功能都要多读几百行、改一处不知道会牵连哪一处——是**速度问题**，不是**正确性问题**。

**联机是另一条轴**：现在 0 行联机代码，属于「还没开始」，不是「做烂了」。它真正会反噬的，是把单机假设（进度存节点、每帧直读键盘、全局只有一个控制者）带上线，见 §2.5。

## 2.5 联机口径：被否定的不是风格，是假设（17:55 补）

**先说事实**：游戏代码里 **0 行联机代码**——全工程没有 `multiplayer`、没有 `@rpc`、没有 `MultiplayerSpawner / MultiplayerSynchronizer`；框架文档要求 W1~W4 先埋的 `is_host()`，代码里也是 **0 处**。`单例` 目录只有 `场景总管.gd`，没有文档里说的「对局数据」。

所以 W5 不是「接上联机」，而是「换掉一批单机假设」。下面六条现在不改，W5 一定返工：

| # | 现在的写法 | 联机时会怎样 |
| --- | --- | --- |
| 1 | 锁孔进度存在锁口节点自己身上（`已插数()`） | 门厅一重载 / 一断线重连，插好的孔全空。框架自己的铁律五要求存「对局数据」，代码没这么做 |
| 2 | 学生每帧直接读全局 `Input` | 四台机器各读各的键盘；主机权威需要「每个 peer 的输入包 → 角色」 |
| 3 | 总管只有一个 `当前控制` + 切相机 | 每台电脑都有自己的玩家，主机不存在「当前是谁」 |
| 4 | HUD 只有一个道具格，谁最后喊就显示谁 | 四个人的道具互相覆盖（`道具格.gd` 注释自己写了这件事） |
| 5 | 搬东西用 `reparent` 挂到搬运者身上 | 搬运者掉线，东西跟着消失；位置靠父子关系算，没法用「携带者 id + 偏移」同步 |
| 6 | 箱子自己写重力、每帧手动改位置 | 各端算出不同结果，且没有权威方 |

**唯一做对的联机伏笔**：所有物件由清单统一构建——只要各端清单一致，编号就能对齐。但主场景2 里手摆的箱子和道具绕过代理，**两端构建顺序不同，编号就会错位**。这不只是整洁问题，是同步事故。

**新增 N 线（和 P0 并行，不改玩法）**：

- [ ] **N0 建「对局数据」autoload**：锁孔进度、门开关、哪些物件被搬走，全部收进这里；节点只负责表现。这是框架铁律五，也是 W5 唯一的地基。
- [ ] **N1 留 `is_host()` 判断位**：所有随机、计时、位移、开门的地方先写条件，函数先永远返回 `true`。W5 只改函数体。
- [ ] **N2 输入包**：角色不再直接读 `Input`，改成「取一个输入包（玩家 id + 动作）」。
- [ ] **N3 HUD 按本地玩家取数**：不再是谁喊显示谁。
- [ ] **N4 内容指纹**：每张图构建完算一个指纹，联机开局前比对，不一致直接拒绝。
- [ ] **N5 手摆两件进清单**：保证各端构建顺序一致。

**验收**：单机行为一点不变；`is_host()` 永远返回 `true` 时，一局能完整跑通。

**文档口径冲突（W5 前必须拍板）**：

- 策划方案写「支持观战与中途补位」，技术框架写「观战、中途补位一律不做」——补位会改掉断线重连的全部设计。
- 策划方案写「服务器随机指定宿管」，技术框架写「局域网 ENet + 主机权威」——没有独立服务器，「服务器」实际是主机。
- 策划方案要 4 人局；技术框架写「追捕者固定 1 名、一对多」——宿管是真人还是 AI，得在 W5 前定死。

## 4. 施工顺序

**两类活，别混着读**：

- **修 bug（真在坏，四处）**：P0-1 真源、P0-2 总管注销、P1-3 箱子落地、P2-2 S 键冲突。这四条不做就会出错。
- **维护升级（不做也能跑，只是以后越改越慢）**：P0-3、P1-1、P1-2、P2-1、P3-1 ~ P3-3。
- **N0 ~ N5 是联机地基**：属于「还没开始」的那部分，单机行为不变。

### P0-1 统一真源
- [ ] **问题**：文档、清单、`run/main_scene` 三处各说各话。
- [ ] **改法**：定下主图后，改 `project.godot` 的 `run/main_scene`；同步 `_项目简报.md`；把主场景2 里手摆的箱子和道具写进物件清单，或明确写一句「场景附件，不进清单」的例外规则。
- [ ] **验收**：F5 启动日志里物件数与清单条数一致，且角色报到数与图上一致。
- [ ] **风险**：把主图改回主场景2 后，主场景3 的梯子测试会失效 → 所以先把梯子测试的入口改成「独立打开主场景3」。

### P0-2 总管减责 + 会注销
- [ ] **问题**：`单例\场景总管.gd` 一个文件干四件事（编号登记、交互转发、换人开关、相机调度），且只登记不注销。钥匙板被 `queue_free` 之后，账本里还留着已删除节点的引用。
- [ ] **改法**：
  1. 拆成两个：`编号簿`（只负责按编号找件）+ `接管器`（换人 + 相机）。
  2. 加一个注销函数，物件 `_exit_tree` 里调用。
  3. 场景重开时清空账本。
- [ ] **验收**：连续重开主图 3 次，控制台不报「编号重了」，不发生 freed instance 报错。
- [ ] **风险**：拆文件会动到所有调用点 → 保留旧函数名做转发，先拆后改名。

### P0-3 补类型契约（最值钱的一步）
- [ ] **问题**：全工程没有 `class_name`，靠 `has_method` 和 `get("编号")` 猜类型。名字打错编译器不报，运行时悄悄失效。
- [ ] **改法**：
  1. 给「可控制角色」建一个基类，学生和宿管继承它；给「可交互物件」建一个基类，门/箱/钥匙板/出口继承它。
  2. 把 `has_method("拉起")`、`has_method("被打中")` 换成 `is 学生` 这类类型判断。
  3. `setup()` 统一成一个参数：传一个字典（或 Godot 的 `Resource`），不要再让代理按类型拼位置参数。
  4. 基类用**英文** `class_name`（文件名和注释继续用中文）。代号宝石的 `状态.gd` 里写了原因：中文文件名走 `preload`，不建议往全局类缓存里塞中文条目。
- [ ] **验收**：把任意一个物件脚本临时改名为错误名字，**编辑器立刻标红**（这就是契约生效的证明）。
- [ ] **风险**：继承链一旦建错，后面很难掰回来 → 先只建两层，别做花活。

### P1-1 抽共用的移动件
- [ ] **问题**：学生和宿管各写一遍重力、土狼时间、跳跃缓冲、顶点定格、爬梯，约 100 行重复。
- [ ] **改法**：做成一个可复用的移动组件（节点或基类方法），两边只保留「不同的参数」。
- [ ] **验收**：改一次重力，两个角色同时生效；两条角色手感没有肉眼可见变化。
- [ ] **风险**：手感是调出来的，抽取时容易碰坏 → 抽之前先用 `数据\通用规则.gd` 把所有数字记下来，抽完逐个对照。

### P1-2 状态机替掉布尔堆
- [ ] **问题**：「瘫痪 / 被扛着 / 被钉住」三个互斥状态用了三个布尔，理论上可以同时为真；`_physics_process` 里有四段几乎一样的「清零速度 + 加重力 + 返回」。
- [ ] **改法**：改成一个枚举状态（正常 / 瘫痪 / 被扛 / 钉住 / 爬梯），同一时刻只允许一个值，速度清零只写一次。
- [ ] **验收**：人为构造「被扛着时被打中」的场景，角色行为有明确定义、不卡死。
- [ ] **风险**：状态迁移漏一条就会卡在某个状态 → 画一张状态迁移表再动手。

### P1-3 箱子的落地判定
- [ ] **问题**：盒子自己写假重力，层号写死 `1`，全工程其他位置都从规则表读。结果是盒子放在第 2 层薄板上会直接穿透。
- [ ] **改法**：层号改成读 `数据\通用规则.gd`；落地判定至少要同时查「地板层 + 薄板层」。
- [ ] **验收**：把盒子分别丢在 1 层地板和 2 层薄板上，都停住不掉。
- [ ] **风险**：盒子一旦改用真物理，和「拿在手上时关闭碰撞」的逻辑要重新对齐。

### P2-1 自测改成测真图
- [ ] **问题**：15/15 通过是真的，但它跑的是旧图 `主场景.tscn`，还直接读 `_amount`、`_user`、`_carried` 这些私有字段。真正的主图没有任何自测。
- [ ] **改法**：
  1. 自测入口改成当前主图。
  2. 只调用公开接口（按编号找件 + 按键），不要再摸私有变量。
  3. 每次改完先跑一遍，确认**改坏时会红**（故意改错一处，看它是不是真的报错，再改回来）。
- [ ] **验收**：自测红过一次（证明它会失败），然后绿。
- [ ] **风险**：坐标写死在新图上会漂 → 尽量按编号找件，不按世界坐标。

### P2-2 输入冲突
- [ ] **问题**：`crawl` 和 `down` 都绑 S 键。
- [ ] **改法**：`down` 改成 S + 方向键下（或改成其他键），保证两个动作不会同时触发。
- [ ] **验收**：站在梯子口按 S，只触发一个动作。
- [ ] **风险**：无。

### P3-1 清死代码
- [ ] **问题**：`场景\楼层代理\楼层代理.gd`（261 行）、`数据\测试\` 下两份楼层清单、`参考资料\参考答案_student.gd`（33KB 旧副本）。
- [ ] **改法**：确认没有脚本引用后删除。删之前用全局搜索确认一遍引用数为 0。
- [ ] **验收**：删完跑一次全量扫描，零报错；主图能正常启动。
- [ ] **风险**：`楼层代理.gd` 可能还被旧测试引用 → 先搜再删。

### P3-2 注释瘦身
- [ ] **问题**：注释占 31%，里面有大量「某天谁说了什么」的对话记录，违反你自己定的注释规矩（只写中性功能说明）。
- [ ] **改法**：删掉对话和日期叙事，只保留「这块代码为什么这么写」的一句话。
- [ ] **验收**：`student.gd` 的注释行数降到 100 行以内，且不影响理解。
- [ ] **风险**：注释删多了会忘掉踩过的坑 → 先把坑迁进更新日志，再删注释。

### P3-3 调试插件别跟着游戏启动

## 5. 不许顺手做的事

1. **不要顺手重命名一大堆变量**。改一个文件就只改那个文件的事，Renaming 单独做一轮。
2. **不要一边重构一边加新玩法**。重构期间跑不起来是正常的，别用「顺便加个功能」掩盖。
3. **不要改 `数据\通用规则.gd` 里的层号定义**（只能改数值，不许在别的文件里复制一份新的）。
4. **不要在没拍板主图之前动测试**，否则测的是空气。
5. **不要自己 commit**。改完让用户看完再提交。

## 8. 新概念（本轮 4 个）

- **Autoload（自动加载单例）**：游戏一启动就自动创建的全局对象，所有脚本都能叫它。像客厅里一块公共白板，方便，但谁都能往上写，最后没人看得懂。
- **Duck typing（鸭子类型）**：不问你是什么类，只问「你会不会这个动作」。好处是灵活，坏处是你写错一个字，编译器不吭声，运行时才翻车。
- **Single Source of Truth（唯一真源）**：同一件事只在一个地方定义。现在文档、清单、`run/main_scene` 三处各说各话，就是反面教材。
- **State machine（状态机）**：把「现在是什么状态」做成一个只能取一个值的开关，替掉一堆可以同时为真的 yes/no。像电梯不会同时显示「上行」和「检修」。

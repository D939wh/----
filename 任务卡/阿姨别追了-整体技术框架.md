## 一、这份文档要解决的问题

策划案第七章写了引擎、节点树、网络、配置、资源五件事，但它回答不了开工第一天的三个问题：

1. **这个功能该写在哪个文件里？** —— 靠目录结构回答（§四）。
2. **两个系统要互相通知，谁去调谁？** —— 靠事件中枢回答（§五.2 + §七）。
3. **哪一块可以先假着，哪一块必须一步到位？** —— 靠分层 + 六周对照表回答（§三 + §十一）。

三条原则贯穿全文，冲突时按顺序让步：

- **能靠信号，不靠引用。** 谁都不许直接伸手掏别人口袋。
- **能靠数据表，不写死代码。** 重量、速度、冷却全在表里，改数值不动逻辑。（已落地，见 §3.2）
- **能靠引擎内置，不自己造。** 物理、动画、计时器、光照都是 Godot 现成的。

## 二、项目概览

夜里十一点半宿舍锁楼，四个学生要把散在各层、被宿管分开藏起来的三块钥匙板，一块一块扛到一楼唯一那扇大门前插进锁孔，凑齐了开门跑去网吧；宿管要拦。核心差异不是「修进度条」，是「背上的重量」——扛起即减速、即发声、即成为活靶；队友本身也是可扛可抛的货物。

### 核心玩法循环

```
熄灯锁楼（P0 点名：谁当宿管）
→ 探索：翻钥匙板、抢快递柜（P1）
→ 搬运：扛起→减速→发声→被追（核心动词）
→ 插锁孔：扛到 1F 大门按 R 插进去，插上即锁、人当场空手（P2）
→ 第 3 块插入：三个孔全亮，唯一那扇楼门弹开（P3）
→ 跑向门口 → 逃出或被拦（P4 结算）
```

### 技术侧的八个「必须有」

下面这张表是本文的验收清单，每一条都能在后面的章节里找到落点。

### 3.1 分层铁律（五条，违反一条就等着返工）

**铁律一：跨场景活着的东西，只放 L5。** 倒计时、插了几个孔、门开没开、谁被拎进值班室——这些都必须活过场景切换，只能放 autoload。放进场景节点里，一换场景就全丢了。

**铁律二：L1 不许出现游戏名词。** `负重组件` 里不能写「如果是钥匙板就……」；它只认 `weight: float` 和一个重量档位枚举。哪天加个「饮水机」要搬，L1 一个字都不用改。

**铁律三：L3 只拼装，不做判断。** 学生节点负责"我身上挂了哪些组件、贴了哪些图"，具体"能不能跳"由 L2 状态机说，"跳多高"由 L1 负重组件算。实体节点里出现大段 if-else，说明判断放错了层。

**铁律四：L0 只有数据，没有逻辑。** 表里放「3 档 = 移速 ×0.45」，不放「重量大于 40 就禁止攀爬」这种判断。但**换算规则本身可以是一张表**——`重量档位.gd` 存的就是"公斤 → 几档 → 罚多少"这条规则，它没有 if，只有一张对照表。

**铁律五：一局之内，同一件事只有一个地方说了算。** 插了几个锁孔只在 `对局数据` 里存一份，锁口节点、HUD、门都只是它的听众。这件事在联机时是生死线——两个地方各存一份，客户端和主机必然对不上。

> 大白话：分层不是为了显得专业，是为了「改一个地方不牵连别的地方」。上面五条铁律全部指向同一件事——把「谁负责什么」钉死，以后想加个新道具、新角色，只需要往对应的格子里塞一格，不用把整栋楼重刷一遍。

### 3.2 数据层现状：规则表 + 地图清单 + 重量档位，以及一条「不建表」的原则

v1 在这里只写了「重量分级表 🆕」。后来我一度打算建四张表（角色库 / 道具库 / 地图库 / 重量档位），而且已经把角色库写出来了——**2026-11-04 主人一句话把方案砍回两张**：

> 「角色库应该是没有用的东西。我们的角色学生他是自我复制的，只要有一个做好的学生，他就可以一直使用——这意味着学生他自己就是一个角色库。图鉴也是同样道理。」

**这句话是对的，而且它改的不是清单，是判断标准。** Godot 的 `.tscn` 本身就是模板：`student.tscn` 做好一个就能复制出无数个，数值写在它自己的脚本上、跟着场景走。再建一张「角色库」表，等于把同一件事记了两遍——而两遍必然分叉。实测就是这样：角色库 24 项、`student.gd` 20 项、`宿管.gd` 13 项，全是重复的；而且角色库那份**零引用、改了不生效**，是一份会骗人的假数据。

所以判断标准从「这个数属于谁」改成更狠的一句：

**能在场景副本里自己带着走的，别建表。**

| 东西 | 怎么存 | 为什么不建表 |
| --- | --- | --- |
| 学生、宿管 | 各自的 `.tscn` + 脚本常量 | 复制场景 = 复制一整套数值。想加「辅导员」，复制学生改两行就行 |
| 箱子、门、梯子、钥匙 | 各自的 `.tscn`，重量是它自己的属性 | 复制一个箱子 = 多一个箱子。想改重量，点开那个箱子改 |

**剩下这三类表，是因为它们真的没法被场景副本表达**：

| 表 | 装什么 | 为什么必须是表 |
| --- | --- | --- |
| `数据/通用规则.gd` | 全工程共用的数：**开门用时**（学生 0.3 / 宿管 1.5）、**钥匙板几块、什么颜色** | 规则。**它对每一张地图都生效**，不属于任何一张图 —— 所以不许写进任何一张图的清单 |
| `数据/正式/物件清单.gd`<br>`数据/测试/物件清单_旧一楼.gd` | **某一张图**上：有哪些门/钥匙板/锁口/检修口/出口，编号、类型、坐标 | 布局。**没有哪个单件场景能表达「这张图有几扇门」**；一张图一份，换图换表。**正式/ 与 测试/ 分开放**，改哪边只影响哪边 |
| `数据/重量档位.gd` | 80 公斤 → 4 档 → 速度 ×0.3、不能跳、不能爬 | 全局换算规则。**它不属于任何一件东西**，是所有重物共用的一把尺子 |

#### 为什么数据不做成「一个装数据的场景」（2026-11-06 主人问过，结论留档）

主人的原始想法：**新建一个场景，把数据全放进去，其他场景去调用它。** 方向是对的（数据只能有一份），差别在「放在什么里面」。

这个想法落地只有两种，各自有代价：

| 落地方式 | 结果 | 代价 |
| --- | --- | --- |
| 每张地图场景里摆一个「数据中心」节点 | 地图 A 一个、地图 B 一个 = **N 份** | 正是要避免的「多份真相」，改 A 的 B 不变 |
| 把它设成 autoload（常驻单例） | 确实只有一份，可行 | ① **必须先有场景树才能读**，工具脚本 / 批量校验 / 自测都得先把游戏跑起来；② 数值只能 `@export`，而这个项目已经踩过「资源型导出存进 `.tscn` 读回 null」（§4.2.1）；③ 改一个数要开编辑器、点节点、翻检查器；④ `git diff` 是一大块资源文本，看不出改了哪个数 |

所以本项目的判据是：

- **纯数值、纯规则** → 脚本里的 `const` 表（`preload` 即读、只读改不坏、diff 一行、不依赖场景树、名字写错编译期就报）。
- **必须靠编辑器摆、或要引用贴图/预制体的数据** → 场景或 `.tres`（Resource）。而且升级成 `.tres` 后**接口仍是 `preload`**，调用方一行不用改。

> 一句话：**场景是「会跑的东西」，数据是「被读的字」。字写在会跑的东西里，就得先让它跑起来才能读；每多一个会跑的地方，就多一份字。**

**什么时候该反过来建表**（现在三条都不满足，先记着）：

- 同类东西多到要横向比较（以后 30 件道具要平衡数值）
- 需要程序生成（随机刷宝箱、随机刷道具）
- 联机要同步（主机下发一份数值，客户端照着算）

**一句话**：表是给「没法用场景表达的东西」准备的，不是给「我觉得整齐」准备的。多一张表就多一份真相，两份真相总有一天对不上——这次的角色库就是个现成的例子。

### 3.3 开门属于场景：角色只发一句话，门自己开

这一条是我判断错、主人纠正的（2026-11-04）：

> 「开门应该属于场景内容，属于场景的数据，角色向场景发送数据、场景回馈。」

> 「角色为什么要收到回话？这个门的场景不是给玩家看的吗？场景收到规矩后自己给自己开门，玩家不是就可以走过去了吗？」

**我原来写的是「快慢是人的手速，该搬进角色脚本」——错的。** 错在两头：数字住错了房子（那是场景的规矩），而且我多加了一层根本不需要的「回话」。

| | 谁负责 | 现状 |
| --- | --- | --- |
| 开门要几秒 | **场景**（`数据/通用规则.gd`），每扇门可单独配 | ✅ 已搬进去 |
| 决定推哪扇门 | 角色，只说一句 `door.press(self)` | ✅ 角色脚本里零个秒数 |
| 门开多快、开到哪儿 | 门自己（`门.gd` 的 `_amount`） | ✅ 一个写死的秒数都没有 |
| 「开好了」这件事怎么让人知道 | **不用回话**：门开够了自己撤掉挡路的 `Blocker`，人撞过去就走过去了 | ✅ 碰撞体消失就是回馈 |

**为什么不需要回执**：玩家看的是门，不是角色的记忆。门板往上缩、变淡、碰撞体撤掉——这三件都是**看得见的**。让角色再收一份「本次开门耗时 1.5 秒」的字典，除了给自己找一个存了却没人读的变量，没有任何用处。能删就删。

所以以后想做一扇「谁都得推 3 秒」的防火门，只在清单里那一行加一句：

```gdscript
{ "编号": "1-防火门", "位置": Vector2(1200, 178), "开门用时": { "求生者": 3.0, "宿管": 3.0 } }
```

`门.gd`、`student.gd`、`宿管.gd` 一个字都不用改。实测（无头、`--fixed-fps 60`）：

| 门 | 谁推 | 清单配的 | 实测 |
| --- | --- | --- | --- |
| 默认门 | 求生者 | 0.3 | 0.30 秒 |
| 默认门 | 宿管 | 1.5 | 1.50 秒 |
| 只覆盖学生 0.8 的门 | 求生者 | 0.8 | 0.80 秒 |
| 只覆盖学生 0.8 的门 | 宿管 | 没覆盖，落回默认 1.5 | 1.50 秒 |
| 防火门（两边 3.0） | 求生者 / 宿管 | 3.0 / 3.0 | 3.00 / 3.00 秒 |

最后两行是同一条规矩的两面：**只写了谁，谁才变；没写的那个继续用默认。**

| 跨层联动 | 锁口只能开**同一层**的门 | 编号点名，开哪扇都行 |
| 场景树 | 4 个看不出在干什么的空 Node2D | 1 个，名字一眼看懂 |

```gdscript
    "三号":      { "类型": "钥匙板", "位置": Vector2(1288, -88) },

```

**「类型」这一栏是唯一让代理认识新东西的地方**：类型 → 场景 → `setup`。现在五种（门 / 钥匙板 / 锁口 / 出口 / 检修口），加第六种就在代理里加一行 `"灯": 灯场景`，其余不动。

#### 4.2.1 编号：一件东西的身份证（2026-11-06，替换原来的「层带」）

建出来的那件东西，编号要挂在它的**感应区**（`Area2D`）上，字段名统一 `编号`。学生按键时 `PickupZone.get_overlapping_areas()` 里拿到的就是这些感应区，读它们的 `编号` 上报，总管按编号查账、把话递过去。

**统一接口**：每件交互物实现 `被按键(键: String, 谁: Node)`。门认 `open_door`，锁口认 `insert_key`，箱子认 `interaction`——**认哪个键是物件自己的事**，代理不再写「先查 door 组、再查 carryable 组」那种 if 链。加新物件时，代理一个字不用改。

**为什么不用「层带」了**：层带是为了回答「这个人在第几层」。按编号以后这个问题根本不用回答——人只报他碰到的东西。原来那套还额外欠着一笔账：地图一改高度，四层楼的层带都得重算（`四楼 -160..16 / 三楼 16..200 / 二楼 200..360 / 一楼 360..600`），算错了就静默地把人判到隔壁层。**能不问的问题，就别造一个数去回答它。**

**踩过的坑（别再犯）**：`@export var 清单: Script` 在 4.7 里能从检查器赋值，但存进 `.tscn` 读回来是 `null`——属性存在、就是没赋上值，代理照旧用默认那张表，看起来一切正常。同理，**中文名的导出属性在 `.tscn` 里赋值也会静默失效**（`清单路径 = "..."` 读不回来，`list_path = "..."` 正常）。导出给编辑器填的东西，属性名一律用英文。

#### 4.2.2 检修口与可以穿过的地板：下楼免费，上楼靠梯（2026-11-06，判据从厚度改成**物理层**，同日主人重排层序）

`交互物/检修口/`：地板缺口上盖的一块**可以穿过的地板**，占物理层第 2 层（位值 2）。站着踩得住，按 S 就穿到下一层。

**判据写在「层」上，不写在「厚度」上（2026-11-06 第二次改，主人指定）**

第一版拿厚度当判据（厚 ≤ 10 算平台、> 10 算地基）。能跑，但每加一块板都得记住它多厚、还得再挂一遍脚本。主人当场指出这太麻烦，问业内怎么做。业内的做法是 **意图在编辑期标注、运行期只读标注** —— 层号就是那个标注：

- **第 1 层「地板」**：墙、楼板、地基。双向挡，任何时候都挡。
- **第 2 层「可以穿过的地板」**：薄板、天窗、检修口盖板、梯子口盖板。踩得住、跳得穿、按 S 掉得下去。

于是「地板按 S 不许下去」不再是判据，而是**结构事实**：按 S 只摘第 2 层，第 1 层一直挂在掩码上，人站在楼板上怎么按都掉不下去。

**「能穿过去」分两半，谁管哪一半必须分清（2026-11-06 主人重排层序后定）**

| 半个问题 | 谁管 | 具体 |
| --- | --- | --- |
| 站得住吗（横向挡不挡） | **物理层** | 人在第 2 层的掩码里 → 被这块板接住 |
| 从下往上能穿吗 | **One Way Collision** | tile 多边形 / `CollisionShape2D` 勾了单向 → 上升不撞头，落到顶点又被接住 |

两半合起来才是主人说的「跳上去也是一个地板，可以站上去」。**层 2 的图块必须同时勾 One Way**：只设层不勾单向，跳上去会撞头；只勾单向不设层 2，按 S 摘不掉它。

**按 S 到底发生什么（全在学生自己身上，平台上一分钱脚本都没有）**

1. `student.gd` 的 `_开始下穿()`：`collision_mask &= ~规则.层_可穿过地板`，同时给 `velocity.y = 20` 一点向下初速（不给的话 `is_on_floor()` 要等下一次 `move_and_slide` 才更新，人会先"贴"一小会儿才落）。
2. `_推进下穿(delta)` 每帧倒计时，到 0.4 秒 `collision_mask |= 规则.层_可穿过地板` 挂回去。
3. **倒计时必须放在 `_physics_process` 所有早退分支之前** —— 瘫痪、被扛、被钉住、被切成宿管，任何一种情况都得恢复；放在后面，人在那 0.4 秒里被打瘫，就会永久停在不撞薄板，从此穿所有薄板，而且不报错。
4. **不用 `await create_timer`**：同一个理由 —— `await` 停在中途，人没了 / 场景重载，后面的代码永远不执行。
5. **用位运算，不用 `set_collision_mask_value(层号, …)`**：那个函数要传「第几层」，主人一重排层序就得改一遍数字；位掩码直接问规则要，摘和挂都是同一句话。

**为什么是 0.4 秒**：按需求反推，恢复碰撞时身体最好已离开盖板体积（身高 44 + 板厚 6 = 50 像素），下落重力 736 下 0.37 秒够，取 0.4 留余量。但**实测 0.3 也能过**（探针场景四，位移 202 像素，没被顶回来）—— 单向碰撞只在"从上方压下来"时挡，人穿过那个平面后恢复碰撞也不会被弹出去。所以这是个安全余量，不是刀口上的数。

- **`交互物/检修口.gd` 只负责摆**：`setup(中心x, 地面y, 宽)` 摆位置、换宽度，并在 `_改宽度` 里把层号和 `one_way_collision` 落死一次（就算 `.tscn` 被改坏，代理一摆出来就纠正回去）。**没有开关、没有计时、没有厚度。**
- **摘层是全局的**：0.4 秒内**所有**可以穿过的地板都不挡人。这是主流取舍（时间极短、只在按下那一帧）；要精确到"只漏脚下那块"得用 `get_last_slide_collision()` 单独关，代码量翻几倍，现在不做。
- **一楼（最底层）没有检修口**，所以掉不出虚空；地图两端靠外墙和一楼地板封死。
- **这个组件里一行绘制都没有**：没有 Sprite/Polygon/ColorRect。物理组件里长美术，以后换贴图要改物理脚本（框架 §6.6 的反面教材，2026-11-05 真犯过一次）。

**梯子洞也盖上它（2026-11-06 补）**：梯子是从楼板的洞里穿上去的，那个洞原本是"挖空"的。人爬到梯子判定框顶端就脱钩，脚正好悬在洞中央 —— 洞上没东西接着，就原路掉回下面那层（实测：一楼爬到 y=225，然后掉回 464，看起来就是"梯子爬不上去"）。

修法不是加"到顶自动跨出"这种特判，而是**给梯子洞也盖一块可以穿过的地板**，清单里加一行即可：

- 它的物理特性是"从下往上能穿过去、从上往下踩得住"。所以爬梯不撞头，爬到顶端正好踩在板上站住。
- 站上去以后**按 S 照样能漏下去** —— 和检修口是同一套「摘第 2 层」，一个字的代码都没多写。
- 爬梯全程**不需要**"临时把层摘掉"：人本来就在第 2 层的掩码里，加上单向多边形，头顶有板也不挡。代码里没有任何"爬的时候关碰撞"的分支。

#### 4.2.3 交互物的贴图必须和判定框同尺寸（2026-11-06）

**规矩：一个交互物的美术范围 = 它的判定范围，差超过 1 像素就算 bug。**

梯子犯过这个错：贴图 **202 × 316**，判定框 **32 × 300**。画面上梯子有 12 格宽，实际只有中间 2 格能抓住 —— 玩家站在梯子画面上按 W，什么都不发生。像素游戏里玩家判断"能不能抓、能不能踩"**只看画**，画大一圈就是骗人，而且这种错不会报错，只能靠人肉发现。

**改法（2026-11-06，主人指定：只动图层，不动判定框）**：`交互物/梯子/梯子.tscn` 的 `Sprite2D` 改成 `position = (0, 8)`、`scale = (0.158416, 0.9494)` —— 202 × 0.158416 = 32.0、316 × 0.9494 = 300.0。改完贴图占 `x ∈ [-16, 16]`、`y ∈ [-142, 158]`，和判定框逐像素重合。

**横压 6.3 倍还看得清吗**：看得清。项目是近邻采样（`default_texture_filter=0`），横档和立柱都是实心色块，压缩丢列不丢色，两根立柱（各 3~4 像素）和横档仍然分明（截图存档在 `D:\Git\调试工具\临时工具\ladder-width-20261106\`）。如果以后觉得窄梯子太细，**重画一张 32 宽的贴图即可，`.tscn` 里那两个数改回 `(1, 1)`**，判定框和代码一个字不用动 —— 这就是"视觉与判定分开存"的好处。

#### 4.2.4 图块画的梯子：图块管看，判定框管爬（2026-11-06，主场景3）

主人用图块把整张图的梯子画出来了。图块能挂物理层，但**梯子不能靠图块让人爬**，原因只有两条，都是引擎事实：

1. `TileMapLayer` 生成的是**静态体**（body），不是 `Area2D`。学生的 `ClimbZone` 靠 `area_entered` 认梯子，静态体撞不出这个信号。
2. 图块的静态体按**碰撞象限合并**（默认 16×16 格一个），一个体盖一大片。就算改成认 body，也分不清「这两格是梯子」还是「旁边那格是墙」。

所以规矩定成这样：**图块只负责「看起来是梯子」，能不能爬由一块 Area2D 判定框说了算。** 一条梯子要摆两次 —— 图块一次（美术），清单一次（判定）。听着像重复，其实是唯一能把两件事都做对的办法：改美术不动手感，调手感不动美术。

实现（三个文件，都不大）：

| `交互物/梯子/梯子.gd`（新） | `setup(中心, 高, 宽, 显示贴图)`：摆位置、换形状大小；`显示贴图` 默认 `false`（图上已画过，再叠一张会错位） |
| `场景/物件代理/物件代理.gd` | `类型场景` 加 `"梯子"`；`_配置` 加一段把「高 / 宽 / 显示贴图」喂进去 |
| `数据/测试/物件清单_主场景3.gd`（新） | 8 条梯子，`位置` = 判定框**中心**，`高` = 画了几格 × 16 |

**两个坑，踩过就别再踩：**

- **`RectangleShape2D` 必须 `duplicate()`**。`梯子.tscn` 里它是 `sub_resource`，**所有实例共用同一份**。直接改 `size`，场上每一把梯子一起变高，而且不报错 —— 只是有一天发现「怎么爬到一半就脱钩了」。

### 4.3 通用读条（界面/读条/）✅ 2026-11-05

**一句话：凡是要长按的事，头顶挂一根条，条上写还剩几秒。** 现在宿管抓人 1.2 秒、学生拉队友 4 秒、自救 2 秒都在用；接下来插钥匙、门口判赢不用另画。

**分工（这条别推翻）**：**谁在长按，谁自己数秒**；条只负责画。

| 谁 | 存什么 | 干什么 |
| --- | --- | --- |
| 长按的人（宿管 / 学生） | `_抓捕进度` / `_救人进度` / `_自救进度` | 唯一的进度真源，每帧 `推进(已用秒)` 报给条 |
| `界面/读条/读条.gd` | 不存进度，只存「总时长 + 已用」 | 画填充、写剩余秒数、跟随那个人头顶 |

**为什么不给条自己一个计时器**：进度存两处，早晚不一致——那时会出现「条走满了但人没被扛起来」这种查不出原因的怪事。

**用法（任何新东西都能抄这几行）**：

```gdscript
const 读条 := preload("res://界面/读条/读条.gd")
var _读条条: CanvasLayer = null                       # 我这根，第一次真的要用时才建

func _我的读条() -> CanvasLayer:
	if _读条条 == null or not is_instance_valid(_读条条):
		_读条条 = 读条.新建(self)
	return _读条条

_我的读条().开始(self, "插钥匙", 2.5)   # 挂在自己头顶；第一个参数传 null = 屏幕下方正中
_我的读条().推进(已用秒)                # 每帧报一次
_我的读条().收()                        # 松手 / 中断 / 完成，三种都要收
```

**三个坑（都是实测踩出来的）**：

1. **被跟的人被 `queue_free` 后，指向他的变量会自己变成 null** —— 所以「这次不跟人（全屏条）」和「跟的人没了」必须靠一个单独的布尔区分，只判 `== null` 会让条永久停在屏幕中间。
2. **换人（F1 / 点击）时脚本走「不受控」分支直接早退**，再没有哪一帧回来推进读条 —— 所以两个角色都在那个分支里主动取消读条，否则条会卡在头顶不动。
3. **中文要自带字体**：Godot 自带 Open Sans 不含汉字，条上写中文会显示成方块。`读条.tscn` 里挂的是 `SystemFont`（微软雅黑优先），改文字样式时别把这行删了。

### 4.4 通关三件套：钥匙板 → 锁口 → 出口 ✅ 2026-11-05

**一句话：搬三块板 → 插进三个孔 → 门弹开 → 站门口 1 秒走人。** 这三样都是「照门那套复制」出来的，没有发明任何新结构。

| 东西 | 谁管进度 | 报什么 | 落到哪 |
| --- | --- | --- | --- |
| **钥匙板** | 自己的重量（继承箱子） | 无（被谁扛、放哪都归学生和场景） | 清单「钥匙板」段 |
| **锁口** | 自己数插孔秒数 | 插满三个孔 → `report("unlock", {门: 名字})` | 清单「锁口」段 |
| **出口** | 自己数站定秒数 | 无（听 `door_finished` 广播，不看谁喊） | 清单「出口」段 |

**为什么分成三样，而不是塞进「门」里**：门管开关、锁口管插孔、出口管跑出去，是三个独立的问题。以后加第二个出口（消防梯、天台晾衣绳），只是清单多一行，门一个字不用改。

**三条链路都走同一个方向**（这是全篇最重要的规矩，加东西也一样）：

```
学生按键 → _上报交互(键, 编号) → 总管 → 按编号找到那件东西 → 它自己干
```

**三个坑（都是这次实测踩出来的）**：

1. **锁口的位置 y 必须填「这块地面」的高度，不是抄门的**。11-05 门填 178、实际地面 208，门板高 96 看不出来，锁板矮就一眼看出飘着 30 像素。改地图后要重新量：把学生从高处扔下去，落在哪就是哪。
2. **可搬运物的初始 y 必须比地面高出一截（≥20px）**。落地靠"从自己身上往下打一条短射线"，出生点已经在地面以下时，射线从地下往更深处探，永远探不到地面 —— 板子会一路掉出屏幕（三号板就这么丢过一次）。
3. **插孔读条中途被打断，必须由锁口自己收尾**：人没了、被打瘫了、玩家切走了、**被挥击打中（`被打中()` 把「钉住」解除）** —— 四种都要 `_中断()` —— 跟读条那条一样，谁数的秒谁负责收，不然条会永久挂在头顶。第四种是 11-11 补的，判断写成「人已经不在钉住状态就作废」：因为钉住只由锁口和人挨打两处改，这一句就等于「插钥匙的人被打断了」。**漏了它的后果不是难看，是牌子被凭空吞掉** —— 人被打飞出 68px、板子掉在地上，两秒后照样判定「插上了」，孔亮起来、地上那块还在。

**数值都在清单里**：插孔 2 秒（`插孔用时`，填 0.1 基本等于按一下就进）、判定区位置大小（`判定区偏移` / `判定区大小`，11-10 起可选，不填用默认块）、钥匙板 15kg（`钥匙板.tscn` 的「重量」）。改这些不用碰代码。

### 5.1 对局数据（对局数据.gd，autoload）🆕

一局游戏的全部「唯一真相」。任何地方想知道「现在几比几」，都来问它，不许自己存一份。

| 成员 | 类型 | 说明 |
| --- | --- | --- |
| `phase` | 枚举 | P0 熄灯 / P1 探索 / P2 运输 / P3 终局 / P4 结算 |
| `time_left` | float | 本局剩余秒数，P0 开始跑 |
| `keys_inserted` | Dictionary | `{"一号": false, "二号": false, "三号": false}` —— 三个孔**各插了没**。用字典不用计数，因为钥匙分编号，计数记不住「哪块插了」 |
| `keys_remaining` | int | 还差几个孔，归 0 时楼门弹开。HUD 和门都读这一个数 |
| `keyplates` | Dictionary | `{钥匙板id: 状态}`（场上 / 被谁扛 / 已插进几号孔） |
| `door_open` | bool | 唯一那扇楼门是否已弹开 |
| `escaped` | Array | 已逃出的玩家 id（可重复，用于评级） |
| `carriers` | Dictionary | `{谁: 扛着什么}`，主机裁定后写入 |
| `locker_next` | float | 下一个快递柜格口弹开的倒计时 |
| `seed` | int | 本局随机种子（钥匙板刷新、家具偏移复现用） |

信号：`phase_changed(new_phase)`、`key_inserted(key_id, total)`、`door_unlocked`、`door_escaped(player_id)`、`match_ended(result)`。

方法：`start_match(seed)`、`reset_match()`、`insert_key(key_id) -> bool`、`register_escape(player_id)`。

> **为什么「哪个孔插了」要单独存一份**：插进去的钥匙板是不可逆的，如果只记在锁口节点自己的变量里，门厅那一块场景一旦重载（联机切场、玩家掉线重连都可能触发），已经插好的孔就全空了——学生会发现自己白跑三趟。放 `对局数据`，才是"活过一切"。
>
> **和 v0.4 的差别**：v0.4 有个 `breaker_progress`（0~1 进度），因为那时是「12 秒读条、打断不清零」。v0.5 改成插上即锁之后，**进度这个概念不存在了**，只剩「插了 / 没插」。字段少一个，联机要同步的东西也少一个。

### 6.1 状态机（组件/状态机/ + 角色/学生/状态/）✅ 2026-11-06 已落地

> **这一节 11-06 之前写的那版（`class_name StateMachine extends Node` + 迁移表 + 一状态一函数）没有落地，也不建议落地。** 实际做出来的是另一版，下面逐条说明差在哪、为什么改。

#### 文件与分工

| 文件 | 装什么 | 行数 |
| --- | --- | --- |
| `组件/状态机/状态机.gd` | 只管「这一帧跑哪个状态」：`加` / `启动` / `切` / `软切` / `跑` | 93 |
| `组件/状态机/状态.gd` | 状态基类：`进入` / `每帧` / `离开`，三个空函数 | 46 |
| `角色/学生/状态/状态名.gd` | 全部状态名常量 —— 拼错就是「常量不存在」，编辑器当场报红 | 17 |
| `角色/学生/状态/*.gd` | 一个状态一个脚本：正常 / 攀爬 / 插钥匙中 / 救人中 / 瘫痪 / 被搬运 / 旁观 / 已逃出（11-11 改名「被拎→被搬运」，行数以编辑器为准） | — |

#### 和旧设想的四处不同（都改过，理由在此）

| 项 | 旧设想 | 实际做法 | 为什么改 |
| --- | --- | --- | --- |
| 容器 | `class_name StateMachine extends Node` + `@export initial_state` | `extends RefCounted`，`_ready` 里 `new` 出来，**不进场景树** | 状态机不需要 `_process`、检查器里没有要填的东西。做成 Node 的代价：每个角色多挂一个节点、多一次「忘了挂 / 忘了填初始状态」的静默失败、还得 `add_child` 才跑得起来 |
| 命名 | `class_name` | **不写 `class_name`**，中文文件名走 `preload`，继承也写路径 `extends "res://组件/状态机/状态.gd"` | 全工程 0 个 `class_name`（这一句原本是孤例）。中文条目进全局类缓存会被按 Latin-1 解读，代号宝石项目踩过 |
| 状态粒度 | 一个状态一个**函数** | 一个状态一个**脚本** | 8 个状态写成 8 个函数，状态机文件迟早长成第二个 700 行。而「一件一个脚本」是这个项目本来的做法（遗物 24 个脚本各一个） |
| 切换判据 | 一张迁移表 + `can_go()` | **抢占**：每帧问实体一句「我该在哪个状态」 | 迁移表要维护 N×N 条边，而学生的状态本质是**一条优先链**（已逃出 > 被搬运 > 瘫痪 > 插钥匙 > 救人 > 攀爬 > 正常）。用链更短，而且和拆之前的早退顺序一一对应 |

#### 抢占：优先级是一张能读的表

```gdscript
# student.gd —— 行序 = 优先级。想调顺序只改这里，不用去别处挪代码块。
func 抢占(现在: String) -> String:
	if 被扛着 or _抛投.在飞:
		return 状态名.被搬运                     # 位置由扛我的人 / 抛投组件摆，我什么都不做
	if 瘫痪:       return 状态名.瘫痪            # 两格血打空（还能按 4 档速度爬）
	if 被钉住:     return 状态名.插钥匙中        # 锁孔前那几秒
	if 现在 == 状态名.救人中:
		return 状态名.救人中                     # 松手/目标没了由 救人中.gd 自己收尾
	if _该攀爬():  return 状态名.攀爬
	return 状态名.正常
```

**这是拆状态机最实在的收益**：拆之前，「谁在谁前面」只存在于 `_physics_process` 里代码块的先后，改优先级要挪代码、还得确认没影响后面的重力与跳跃。

#### 两种切换，对应原来的两种写法

| 方法 | 语义 | 对应拆之前的什么 |
| --- | --- | --- |
| `切(名字)` | 硬切，切完本帧到此为止 | 各分支末尾的 `return` |
| `软切(名字)` | 软切，切完本帧继续跑新状态 | 「掉出分支后接着往下跑」 |

**绝大多数地方用 `切`。** 本工程目前没有一处用到 `软切` —— 留着是因为改成「同帧连续处理」时不用重写状态机。

#### 加一个新状态 = 三步

1. 在 `状态名.gd` 加一行常量（拼错就报红）；
2. 新建 `角色/学生/状态/<名字>.gd`，`extends "res://组件/状态机/状态.gd"`，写 `进入` / `每帧` / `离开`；
3. 在 `student.gd` 的 `_搭状态机()` 里 `加()` 一行，在 `抢占()` 里给它一个位置。

**其余状态一个字不用改。** 这就是拆它的理由。

#### 硬规矩

- **状态里不许直接改别的状态的东西。** 要换状态只能 `机器().切("名字")`；公共动作（换色、开读条、reparent）调角色的公开方法。
- **`机器().当前()` 只给外部读数用**（调试面板、自测）。拿它写游戏规则，就又把 if 链搬回来了。
- **每帧能干活的只有当前状态。** 状态机在「切」的当帧不跑新状态的 `每帧`，从下一帧开始 —— 差这一帧的感觉，见 §10.1 末尾的实测说明。
- **宿管也要用同一套，但必须是两套独立实例**（各自 `new` 一台状态机），别共用一张状态表。宿管 **11-09 已套**（手控/待机/巡逻/追击），见 §10.2。

### 6.2 负重组件（组件/负重.gd）🆕 —— 规则已跑通，容器还没建

四档重量的换算，现在收在 `数据/重量档位.gd` 那一张表里，别的地方不许再写减速公式。

| 档位 | 触发重量 | 移速倍率 | 慢走 | 跳跃 | 攀爬 | 声响半径 | 数据来源 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1 档 | ≤ 20 kg | ×0.9 | 可 | 正常 | 可 | +0 | `重量档位.gd` |
| 2 档 | 20–40 kg | ×0.6 | 禁 | 高度减半 | 禁 | +2 m | 同上 |
| 3 档 | 40–60 kg | ×0.45 | 禁 | 禁 | 禁（只能拖行） | +2 m | 同上 |
| 4 档 | > 60 kg | ×0.3 | 禁 | 禁 | 禁（只能拖行） | +3 m | 同上 |

（2026-11-03 由「轻/中/重/超重」改为编号 1~4，每档 20 kg 一刀；现行的唯一真源是 `阿姨别追/数据/重量档位.gd`。）

**已实测的三条**（不是推算）：扛 80 kg 纸箱，走速 315 → 94.5 像素/秒；按空格起跳，抬升 **0 像素**；在梯子上按 W，位移 **0 像素**。

```gdscript
class_name CarryComponent extends Node

@export var tables: CarryTable          # 指向 数据/重量档位.gd

var carried: Node = null                # 当前扛着什么（null = 空手）
var tier: int = 0                       # 0 空手 / 1、2、3、4 = 档号

signal tier_changed(new_tier: int)
signal carried_changed(item)

func pick_up(item: Node) -> bool        # 拿起：查表设档位，转交给 可搬运基类
func drop() -> void                     # 放下 / 被打掉落
func throw_charge(delta) -> void        # 蓄力 0.5 秒
func release_throw(dir: Vector2) -> void
func speed_multiplier() -> float        # 给移动代码问的
func can_jump() -> bool
func can_climb() -> bool
```

**为什么单拎出来**：四个档位 × 六种限制 = 24 条规则，散在移动、跳跃、攀爬、AI、HUD 五个文件里，改一次数值要改五处，必然改漏。收成一个文件，改表就全局生效——这也是策划案第九章「改一个负重系数全局生效」那条验收的具体落点。

**角色被动的叠加**：游戏宅「负重减速减半」、吃货「所有负重减速 −5%」这类被动，**不许改 CarryComponent 内部的常量**，而是由状态机在读 `speed_multiplier()` 之后再乘一个角色修正系数。组件保持中立，角色差异留在角色层。

### 6.3 状态组件（组件/状态组件.gd）

学生只有两格血，但状态有三层：**正常 → 被逮（掉拖鞋、留脚印）→ 蹲地（可被扛、有 90 秒倒计时）→ 被拎（关值班室）**。

```gdscript
class_name HealthComponent extends Node

@export var max_hp: int = 2
var hp: int

signal damaged(amount: int, from_direction: Vector2)
signal downed()                 # 进入蹲地
signal caught()                 # 被拎走
signal revived()
```

组件只管**数值 + 信号**。「掉拖鞋」「留脚印」「去饱化画面」这些表现全部由实体自己监听信号去做——组件不认识拖鞋。

### 6.4 感知组件（组件/感知.gd）

宿管专用，但写成通用。

> **现状（2026-11-10）**：听觉已经能用，但没拆成 `组件/感知.gd` —— 监听与判断活在 `宿管.gd` 的 `_听见声音()`（音量按 `数据/声音表.gd` 现算，低于 0.15 不反应，记忆 6 秒，自己脚下 4px 内的声不回听）。视野仍是圆形察觉圈（`DetectZone` 360px）。下面是目标形态。
> 「只记方向不记距离」是给 HUD 表现层的说法 —— 逻辑层必须记完整坐标，不然搜索状态没有地方可走。

- **视野**：`Area2D` 扇形 + `RayCast2D` 遮挡采样（墙体挡视线）。角度 100°、距离 9 m，写在宿管自己的脚本里——**不建表**，因为宿管只有一个，复制它就是新角色。（⏳ 未做）
- **听觉**：监听 `事件中枢.noise_made`，按 `radius` 判断是否听见，只记方向不记距离。（✅ 判定已落地，见上）
- **输出**：`can_see(target)`、`last_known_position`、`heard_something(pos, radius)`。（🌗 现在的对应物：`_看得见的目标()` / `_听觉目标` / `_听见声音()`，都在 `宿管.gd`）

**性能注意**：视野检测不要每帧对每个学生做射线，按 6 Hz 节流即可——这是 §十一 性能目标的实际抓手。

### 6.5 读条 / 蓄力（「松手结算」那半 ✅ 2026-11-09 落地）

「按住不放」其实是两种语义，别混成一件事：

| 语义 | 例子 | 谁来管 |
|---|---|---|
| **松手才结算**（按多久攒多大力） | 抛投：按住 F 蓄力，松手扔出去 | ✅ `组件/蓄力/蓄力.gd` |
| **按满就完成**（不到点就白按） | 插钥匙 0.6 s、拉起队友 4 s、被抓 1.2 s、撑起来 6 s | ⏳ 还没拆，仍在各调用处自己数秒 |

实际接口（`组件/蓄力/蓄力.gd`，RefCounted，**不写 `class_name`**）：

```gdscript
var 满蓄时长: float = 0.8
var 读条条: CanvasLayer = null      # 塞一根 `界面/读条/` 的节点进来，蓄力时自动显示
var 读条标题: String = "蓄力"

func 开始(宿主: Node2D) -> void     # 已经在蓄力时不重置，连按不会把攒好的力打回 0
func 推进(delta: float) -> void     # 攒满封顶，比例永远 0~1
func 松开() -> float                # 返回 0~1，并把状态清干净
func 取消() -> void                 # 被打断 / 切状态 / 东西脱手
func 在蓄力() -> bool
func 比例() -> float
func 满了() -> bool
```

**`取消()` 有个前提（11-11 修）**：**没在蓄力时它什么都不做，尤其不碰读条。**
学生的力条和锁口插钥匙借的是**同一根** `界面/读条/` 节点，原来的 `取消()` 不看自己在不在蓄力，闭眼就是一句 `读条条.收()`；于是「按 R 插钥匙 → 状态从正常切进插钥匙中 → `正常.离开()` 调 `_取消蓄力()`」会把锁口刚点亮的读条收掉 —— 症状是**插钥匙的读条从来没显示过**（一闪就没）。改法只要一句 `if not _在蓄: return`，仍然只说「我有没有在蓄力」，不认识锁口。**教训：共用同一根条的时候，「收尾」这个动作必须带前置条件。**

它只记时间：不认识箱子、不认识人、连按的是哪个键都不知道（谁调 `推进` 谁自己报时间）。力怎么变成初速、抛物线怎么飞，是 `组件/抛投/` 的事。

**还没做的那半**：原纸面契约里 `keep_on_interrupt`（拉起队友保留进度 / 抓捕被打断就重置）这个开关，对应的是上面第二行那批「按满才完成」的动作。做的时候照 `组件/蓄力/` 的样子来：RefCounted + `preload`，**别写 `class_name`**（理由见 §6.1 的命名规矩）。

### 6.6 光照与可见性（不进组件，走渲染层）

策划案 6.8 的三条规则（手电照到才能识别可交互物、关灯完全隐没、光就是代价），技术上靠三样东西拼：

| 需求 | 实现 |
| --- | --- |
| 全楼压黑 | 关卡根节点挂 `CanvasModulate`，颜色压到接近黑 |
| 光锥内看得清 | `PointLight2D`（学生自发光 1.5 m）+ `SpotLight2D`（手电 6 m × 25°） |
| 墙体挡光 | `LightOccluder2D` 跟着 TileMap 的墙体一起画 |
| 关灯找不到东西 | 可交互物的"识别高亮"（描边/微光）挂在**手电光锥内的检测**上，而不是永远显示 |
| 宿管能看见光点 | 手电开启时，在宿管侧生成一个"光源标记"，12 m 内可见——这是给对手的信息，不是给自己的 |

> 大白话：Godot 的光照不是「照亮贴图」那么简单，它同时是一套**信息权限系统**。谁的光照到谁，谁就有权看见细节。本作把"信息不对称"这件事直接写进了渲染层，所以光不是装饰，是玩法。

```
        钥匙板 ──────▶│                 │◀────── 锁口
        快递柜 ──────▶│   事件中枢       │◀────── 学生
```

**读图规矩**：横线只有"往中枢发"，竖线只有"从中枢听"。**任意两个实体之间没有直连的线**——钥匙板永远不需要认识 HUD，HUD 也永远不需要知道钥匙板长什么样。

## 八、核心循环与场景流

```
主菜单 →（单机 / 建房 / 加入）→ 对局数据.start_match(seed)
   → 场景切换.go("对局/game.tscn")

       ├─ 钥匙板：6 候选点随机 3 块，分布在不同楼层
       ├─ 快递柜：8 格口，开局弹开 3 个
       └─ P0 点名（0:00–0:15）：随机指定宿管，灯逐段熄灭
```

## 九、网络同步与切场

### 9.1 分工表

方案：**主机权威（Host-Authoritative）+ ENet + 20 Hz 快照**。选它而不是帧同步的理由：5 人小局、状态量小、对确定性要求低，实现成本最低。

| 内容 | 谁说了算 | 客户端做什么 |
| --- | --- | --- |
| 本机移动 | 客户端预测 | 立即动，收到主机校正再回滚 |
| 他人移动 | 主机 | 线性插值 + 200 ms 延迟缓冲 |
| 谁扛着什么 | 主机 | 只播动作与重量表现，不自判 |
| 锁孔进度 | 主机 | 只播亮几个孔，不自增 |
| 快递柜弹开 | 主机 | 只播柜门与蓝光 |
| 门是否弹开 | 主机 | 只播门开与长音 |
| 伤害 / 抓捕 / 逃出 | 主机 | 只播受击与结算 |
| 随机（钥匙板位置） | 主机按 seed 生成 | 收结果，不自己 roll |

**反作弊**：主机端校验移速上限与交互距离，超限回滚并记一笔。

**分层的好处在这里兑现**：因为所有状态都已经收在 `对局数据` 里，W5 要做的只是"把本地这份账本改成主机那份账本的镜像"。如果 W1~W4 把状态散在十个节点里，W5 就不是加一周，是返工三周。

### 9.2 切场流程与加载屏障

**先纠正一个常见误解**：本作不是"每个玩家一个场景"，是**一张地图 + 五个摄像机**。四个人和宿管在同一栋楼里，谁在几楼只是他的镜头在看哪里。所以问题不是"各自加载不同的地图"，而是"五台机器怎么保证看到的是同一栋楼，以及谁在什么时候才开始玩"。

真正会出错的地方只有一句话：**客户端还没加载完，主机已经开始 spawn 角色 → 那台机器永远收不到那几个角色，开局就是"看不见人但被打"**。所以必须有一道屏障，等齐所有人。

```
主机                                    客户端 ×4
 │  match_start(seed, map_id)  ────────▶ │
 │                                       │  本地加载全楼（1–2 s）
 │  ◀──────── ready（谁好了谁报）         │
 │                                       │
 ├── 加载屏障：收齐 5/5 才放行 ──────────┤
 │                                       │
 │  spawn（5 角色 + 道具 + 锁口）────────▶ │
 │  P0 熄灯，倒计时开始         ────────▶ │
```

**四条硬规矩，每条对应一个真实会翻车的地方：**

| 规矩 | 为什么 |
| --- | --- |
| **禁止用 `change_scene_to_file` 切场** | 换场景会销毁整棵节点树，绑在节点路径上的 `MultiplayerSpawner`、`@rpc` 全部失效，之后一个同步都收不到 |
| **常驻根 + World 空容器** | 根场景常驻，切图只清空 `World` 的子节点；网络连接与单例毫发无伤（见下方结构） |
| **传 seed，不传地图** | 主机只发 `seed=8842` + `map_id`，五台各自用同一种子生成钥匙板位置与家具偏移。几十字节而不是几十兆，还天然保证一致 |
| **`MultiplayerSpawner` 路径要稳定** | 挂 `World/Actors`，每张图都留这个路径，换图不改代码 |

```
main.tscn（常驻根，从头到尾不换）
├── 网络层（MultiplayerAPI 相关，永不被销毁）
└── World（空 Node2D 容器，切图只替换它的子节点）
    ├── Map（当前楼层实例）
    └── Actors（MultiplayerSpawner 的 spawn_path）
```

```gdscript
# 场景切换.gd —— 联机版切场
const MAP_LIB := {&"dorm_5f": "res://场景/对局/game.tscn"}

func host_start_match(map_id: StringName, seed: int) -> void:
    if not 网络会话.is_host(): return
    _load_match.rpc(map_id, seed)          # 全体同时开始加载

@rpc("authority", "call_local", "reliable")
func _load_match(map_id: StringName, seed: int) -> void:
    Root.World.clear()                      # 只清子节点，不换场景
    var map := (load(MAP_LIB[map_id]) as PackedScene).instantiate()
    Root.World.add_child(map)
    map.build_from_seed(seed)               # 五台算出完全一致的钥匙板/锁口布局
    _report_ready.rpc_id(1)                 # 向主机报到
```

```gdscript
# 对局数据.gd —— 主机侧收 ready，收齐才开局
var ready_peers: Array[int] = []

@rpc("any_peer", "call_remote", "reliable")
func _report_ready() -> void:
    var id := multiplayer.get_remote_sender_id()
    if id not in ready_peers: ready_peers.append(id)
    if ready_peers.size() + 1 >= 网络会话.peers.size():   # +1 是主机自己
        _begin_match.rpc()

# 超时保护：8 秒没齐 → 踢掉那台并广播，别让四个人干等
```

**为什么单机不用写两套**：`网络会话.is_host()` 单机恒为 `true`，所以上面这套代码单机跑就是"立即 ready、立即开局"，一行分支都不用加。

### 9.3 视角隔离：一个场景，三种归属

"不同玩家视角"要拆成三层看，只有中间那层需要同步。混在一起想，就会做出"每人一份地图"这种灾难设计。

| 层 | 归属 | 内容 | 怎么同步 |
| --- | --- | --- | --- |
| **地图** | 必须五台一致 | 房间、楼梯、锁口、钥匙板藏点 | 不传模型，传 seed，各自生成 |
| **实体** | 主机权威 | 角色位置、谁扛着什么、插了几个孔 | 主机 spawn + 20 Hz 快照 |
| **视角** | 各算各的 | 相机跟谁、手电照到哪、哪层已探索 | **一个字节都不同步** |

视角层的具体做法：

- **相机**：每个客户端只 `enabled` 自己那台 `Camera2D`，别人的相机整个不创建。
- **手电与光锥**：视觉全本地算，但**"手电是开着还是关着"这个状态必须同步**——因为宿管要能看见 12 m 内的光点。规则简单（就是个距离判断），不需要主机裁定。
- **已探索区域 / 小地图**：只存在本地字典里，不上传、不下发。
- **屏幕外的楼层**：靠 `visible = false` 关渲染，**碰撞体与 `AudioStreamPlayer2D` 照常运行**。

**三条不许做的事：**

1. **不许把"楼层"做成可切换的场景。** 一旦按楼层切场，站在 3 楼和站在 1 楼的两个玩家就在两个不同的场景里了，谁也看不见谁。整栋楼就是**一个**场景、一张图，不按楼层切文件；哪一层看不见，只 `visible = false`，不是换场景。
2. **不许"看不见就不加载"。** 那是 3D 开放世界省内存的办法。本作的核心情报之一是**声音**——隔两层楼听见楼上脚步，是学生判断宿管位置的主要手段。卸载了 5 楼，你就什么都听不见，玩法直接少一半。**剔除只剔渲染，不剔音频和逻辑。**
3. **不许把"黑暗"当成本地作弊开关。** `CanvasModulate` 压黑只是表现；真正的可见性由光照 + `LightOccluder2D` 决定。局域网自娱项目不做反作弊，但别把关键判定建立在客户端表现上。

#### 设计里有、还没做

| 状态 | 现状与说明 |
| --- | --- |
| 被逮（挨 1 格还有行动力） | ❌ 现在两格血，掉 1 格仍然是「正常」。策划案里的「慢速移动、留脚印」还没实现 |

#### 为什么「负重」不在这两栏里 —— 这是 11-06 改掉的一处旧设定

原来这张表把 `空手` 和 `负重` 并列成两个状态。但看代码事实：

- 负重的时候人**照样能走、能跳（矮）、1 档还能爬**；
- 也就是说负重**改变参数，不改变能干什么**。

真做成状态就会炸成「空手走 / 负重走 / 空手跳 / 负重跳 / 空手爬 / 1 档爬 / 2 档爬」—— 状态机最经典的死法：**状态爆炸**。

所以现在分两层：

| 层 | 是什么 | 例子 |
| --- | --- | --- |
| **状态**（互斥，决定控制权归谁） | 同一时刻只有一个 | 正常 / 攀爬 / 瘫痪 / 被搬运 …… |
| **参数**（可叠加，只改数值） | 随时可叠加 | 负重档位（`_移速倍率` / `_跳跃高度倍率` / `_可否攀爬`，来自 `数据/重量档位.gd`）、慢走、下穿倒计时 |

#### 硬规矩

- `插钥匙中` 与 `负重` 互斥（插进去那一瞬钥匙板交给锁口、人立刻空手）；
- `瘫痪` 与 `攀爬` 天然互斥（瘫了根本不进攀爬，抢占先给瘫痪）；
- **能不能待在某个状态，只在 `抢占()` 回答一次**，不要在状态自己的 `每帧` 里再判一遍「我该不该在这」。

#### 一条实测（怕以后有人不信「差一帧也算差」）

拆完用同一个探针量了拆前 / 拆后两组数，**五项一字不差**：走 30 帧位移 134.64、松手滑行 20.25、满跳离地 94.95、负重 50kg 走 30 帧 66.73、梯上速度 -70.0。明细见《项目更新日志》【2026-11-06 18:30】。

## 十二、别重复发明（引擎已经有的）

新手项目最贵的浪费是手搓引擎功能。这张表是"先查表再动手"。

| 你要的功能 | Godot 现成的 | 别自己写 |
| --- | --- | --- |
| 横版移动与坡道 | `CharacterBody2D` + `move_and_slide()` | 别手动算碰撞 |
| 可以穿过的地板 | 物理层 2 + `CollisionShape2D` 的 one_way 勾选（缺一不可） | 别用 Area 判定 |
| 动画切换 | `AnimationPlayer` / `AnimatedSprite2D` | 别用 Timer 数帧 |
| 计时 | `Timer` 节点、`SceneTreeTimer` | 别用累加 delta 判秒 |
| 交互触发 | `Area2D` + `body_entered` | 别用距离 sqrt 每帧算 |
| 地图与碰撞 | `TileMapLayer` + 物理层 | 别一格一节点 |

## 十四、范围锁（明确不做）

不属于「节点 / 状态机 / 信号 / 地图 / 搬运 / 光照」这六项练手目标的功能，一律不做：

不做商业化、不做付费、不做成就、不做排位赛季、不做本地化、不做公网联机、不做账号系统、不做回放系统、不做地图编辑器。

> **手机端不是「不做」，是「放缓到最后做」**（2026-11-05 主人定，原话：「手机端要放缓做，要到最后做，只是我们开发的时候不考虑。因为由我来考虑，我做框架的时候我都会给我们留后路的。」）。
> **开发期不考虑手机**：分辨率、地图尺寸、实例数量、美术规格按电脑定，不为手机让路、不提前降配。
> **移植排在版本做完之后**；**结构后路由主人在框架里铺**——后路是指「将来能改」，不是「现在就得省」。所以像「死物不进实例、活物才建节点」这类设计照样做，理由永远是**维护成本**（改一处灯不用改几十处），手机只是顺带的好处。
> **别做两件事**：① 别自作主张按手机预算砍设计；② 别把已留的后路拆掉。

省下来的时间全部投到 §三 的六层里。**范围失控是本项目最大的风险，比技术难度大得多。**
